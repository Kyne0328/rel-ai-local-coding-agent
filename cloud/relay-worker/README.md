# Rel.AI Cloud Relay Worker

Rel.AI Cloud is the remote MCP and OAuth boundary for the Electron-first Rel.AI architecture. It provides:

- OAuth 2.1 authorization code flow with mandatory PKCE (`S256`)
- OAuth protected-resource and authorization-server discovery metadata
- dynamic registration for public MCP clients
- short-lived access tokens and rotating refresh tokens
- resource-bound and scope-bound `/mcp` authorization
- Ed25519 proof-of-possession device registration
- short-lived, single-use desktop pairing codes
- one-time WebSocket connection tickets
- one hibernatable Durable Object WebSocket relay per device
- bounded forwarding only to the connected desktop's local `/mcp` service
- no repository payload persistence in D1

The public MCP endpoint is:

```text
https://rel-ai-cloud.kynskie13.workers.dev/mcp
```

## Install and validate

```bash
cd cloud/relay-worker
npm install
npm run check
npm run test:local-flow
```

`npm run check` runs the unit tests and a Wrangler deployment dry-run. `npm run test:local-flow` applies local D1 migrations and exercises discovery, dynamic client registration, PKCE authorization, pairing, access-token validation, refresh-token rotation, revocation, and MCP enforcement against a local Worker.

## OAuth discovery

Protected Resource Metadata:

```http
GET /.well-known/oauth-protected-resource
GET /.well-known/oauth-protected-resource/mcp
```

Authorization Server Metadata:

```http
GET /.well-known/oauth-authorization-server
```

The metadata advertises:

- authorization endpoint: `/authorize`
- token endpoint: `/token`
- dynamic registration endpoint: `/register`
- revocation endpoint: `/revoke`
- grant types: `authorization_code`, `refresh_token`
- PKCE method: `S256`
- scopes: `mcp`, `offline_access`
- token endpoint authentication method: `none`

## ChatGPT authorization flow

1. ChatGPT requests `/mcp` without a token.
2. The Worker returns `401` with a `WWW-Authenticate` header containing the Protected Resource Metadata URL.
3. ChatGPT discovers the OAuth endpoints and dynamically registers a public client.
4. ChatGPT starts `/authorize` with `resource`, `state`, and a PKCE challenge.
5. The authorization page asks the user for the single-use pairing code generated by the Rel.AI desktop app.
6. The Worker atomically consumes the pairing code and returns a short-lived authorization code to the exact registered redirect URI.
7. ChatGPT exchanges the code at `/token` using the PKCE verifier.
8. The Worker issues an opaque one-hour access token and, when `offline_access` was requested, a rotating refresh token.
9. Every `/mcp` request validates the token's hash, expiry, revocation state, client state, device state, scope, and resource audience.

The removed `/v1/pairings/claim` endpoint no longer issues public bearer tokens directly.

## Dynamic client registration

```http
POST /register
Content-Type: application/json

{
  "redirect_uris": ["https://client.example/oauth/callback"],
  "client_name": "Example MCP client",
  "token_endpoint_auth_method": "none",
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"]
}
```

Only public clients are accepted. Redirect URIs must use HTTPS, except for HTTP loopback addresses used in local development. Redirect URIs are matched exactly during authorization and token exchange.

## Device registration protocol

Electron generates an Ed25519 key pair and retains the private key locally.

1. Create a challenge:

```http
POST /v1/devices/register/challenge
Content-Type: application/json
```

```json
{
  "public_key_jwk": {
    "kty": "OKP",
    "crv": "Ed25519",
    "x": "<base64url-public-key>"
  }
}
```

2. Sign the returned UTF-8 `challenge` with the local private key.
3. Complete registration:

```http
POST /v1/devices/register/complete
Content-Type: application/json
```

```json
{
  "challenge_id": "<challenge-id>",
  "signature": "<base64url-signature>"
}
```

The response contains a long-lived `device_token`. Electron stores it with operating-system credential encryption; it is not exposed to the renderer.

## Pairing code

```http
POST /v1/devices/pairing-code
Authorization: Bearer <device-token>
```

The returned code expires after ten minutes and can be used once on `/authorize`. It binds one OAuth grant to one active desktop device.

## Device WebSocket

Exchange the device token for a one-time connection ticket:

```http
POST /v1/devices/connection-ticket
Authorization: Bearer <device-token>
```

The ticket expires after 60 seconds and is consumed by the first WebSocket connection attempt. Electron uses the returned `websocket_protocol` value when connecting to:

```text
wss://rel-ai-cloud.kynskie13.workers.dev/v1/devices/connect
```

The Worker sends request envelopes containing only the method, `/mcp` path, allowlisted headers, request ID, and a bounded base64 body. Electron replaces cloud authorization with its local bearer token and forwards only to `http://127.0.0.1:<port>/mcp`.

The relay must never become a generic URL proxy.

## Token and data policy

D1 stores only:

- OAuth client metadata
- hashes of authorization codes, access tokens, refresh tokens, device tokens, pairing codes, and connection tickets
- device public keys and identifiers
- exact redirect URIs, scopes, resource audience, timestamps, and revocation state

Plaintext bearer tokens are returned once and are not stored. MCP request bodies, responses, repository paths, source files, and command output pass through memory and are not written to D1.
